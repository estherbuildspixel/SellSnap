# Component Builder Skill

Load this skill whenever you are creating or modifying a React component in SellSnap. It tells you where the component goes, how it is structured, and how to wire it to the design system without reinventing anything.

**SellSnap does not use Tailwind. There is no `tailwind.config.ts`, no `class-variance-authority`, and no `clsx`.** Styling is CSS Modules plus CSS custom properties from `tokens/tokens.css`. If any example you remember from another project uses Tailwind utilities, ignore it.

---

## Before You Start

1. Read `.agents/rules/design-system.md`. It is the authority and it is loaded always. Components that ignore it get rejected at review.
2. Search `components/` before adding anything. Two slightly different `Button` components is how codebases rot. If a primitive almost fits, add a variant instead.
3. Check `tokens/tokens.css` for the variables you intend to use. If the token you need does not exist, stop and ask. Do not invent a value and do not edit the token file (it is auto-generated by `tokens/convert-tokens.js`).

---

## The Four Non-Negotiables

1. **CSS Modules only.** One `ComponentName.module.css` next to `ComponentName.tsx`. No inline `style={{}}` except genuinely dynamic values (a progress bar width from a number, a computed background position).
2. **Tokens only.** Colors and typography always via `var(--…)`. No hex, no `hsl()` literals, no px font sizes in component CSS.
3. **Mobile-first.** Default rules target mobile. Layer desktop with `@media (min-width: 768px)`. Touch targets minimum 44px tall.
4. **Server by default.** `"use client"` is a deliberate cost, not a default.

---

## Where Components Live

```
components/
├── ui/                  primitives: Button, Input, Card, Badge, Avatar
├── product/             product domain only (ProductCard, PriceTag, ProductImage)
├── dashboard/           seller dashboard only (OrdersTable, ProductList)
└── shared/              composites used by more than one domain (EmptyState, PageHeader)
```

If a component is used exactly once and is complex, keep it beside its page at `app/<route>/_components/`. Promote it to `components/` when a second caller appears. Do not promote preemptively.

---

## File Layout

Every component is two files, same basename, same folder:

```
components/ui/Button.tsx
components/ui/Button.module.css
```

`tokens/tokens.css` is global and imported once in the root layout. It is the only stylesheet that is not a module, and you never edit it.

## Component Template

```tsx
// components/<folder>/<ComponentName>.tsx

import { cn } from '@/lib/cn';
import styles from './<ComponentName>.module.css';

type <ComponentName>Props = {
  // Required props first, optional after.
  children?: React.ReactNode;
  className?: string;
};

export function <ComponentName>({ children, className }: <ComponentName>Props) {
  return (
    <div className={cn(styles.root, className)}>
      {children}
    </div>
  );
}
```

```css
/* components/<folder>/<ComponentName>.module.css */

.root {
  display: flex;
  align-items: center;
  gap: 8px;
  color: var(--color-on-surface-color);
}
```

Notes:
- **Named export.** Default exports make renaming harder and break tooling.
- **Props type above the component**, named `<ComponentName>Props`, required before optional.
- **Always accept `className`** on a component with a single root element and merge it with `cn()`, last, so callers can adjust layout without forking the component.
- **Keep the root class first** in `cn()` so the caller's class can override it.

### The `cn` helper

`cn` has no dependencies — it just joins truthy strings. If `lib/cn.ts` does not exist yet, create it:

```ts
export function cn(...parts: Array<string | false | null | undefined>): string {
  return parts.filter(Boolean).join(' ');
}
```

Import from `@/lib/cn`. Related shared helpers live in `lib/utils.ts`. Do not pull in `clsx` or `tailwind-merge` — neither is installed and neither is wanted.

## Server vs. Client Components

Default to server. Add `"use client"` only when the component needs one of:

- React state (`useState`, `useReducer`)
- Effects (`useEffect`, `useLayoutEffect`)
- Browser-only APIs (`window`, `document`, `localStorage`)
- Event handlers beyond a plain link (`onClick`, `onChange`, form `action`)
- Context consumption for interactivity

When you do add it, it goes on the first line of the file. Never add it defensively.

Keep the client boundary as low in the tree as possible. A page that is mostly static with one interactive control should stay a server component; the control should not.

## Styling

### Colors — semantic roles only

Use the semantic role variables. They re-point automatically for dark theme, which is why you must not touch the primitive layer.

```css
/* correct */
color: var(--color-on-surface-color);
background: var(--color-surface-container-low-color);
border: 1px solid var(--color-outline-variant-color);

/* wrong — the token does not exist, so the declaration is silently dropped */
color: var(--color-surface-container-low);

/* wrong */
color: #1a1a1a;
color: var(--primitive-color-light-on-surface-color);
```

Every semantic role carries a `-color` suffix. If you are unsure whether a variable exists, check `tokens/tokens.css` rather than guessing — an unresolvable `var()` fails silently at computed-value time and the property is simply discarded, which looks like a styling bug that nobody can find.

The roles available in `tokens/tokens.css`:

| Need | Variable |
|---|---|
| Brand / action fill | `--color-primary-color`, `--color-on-primary-color` |
| Secondary action fill | `--color-secondary-color`, `--color-on-secondary-color` |
| Tertiary / accent | `--color-tertiary-color`, `--color-on-tertiary-color` |
| Error / danger | `--color-error-color`, `--color-on-error-color` |
| Page background | `--color-background-color`, `--color-on-background-color` |
| Raised surface | `--color-surface-color`, `--color-on-surface-color` |
| Muted surface / divider | `--color-surface-variant-color`, `--color-on-surface-variant-color` |
| Elevation ladder | `--color-surface-container-lowest-color` … `--color-surface-container-highest-color` |
| Borders, icons | `--color-outline-color`, `--color-outline-variant-color` |

Never reference `--primitive-color-*` in component CSS. The token file says so explicitly, and the dark-theme block only overrides the semantic roles.

### Known broken tokens

The error ramps and several dark-theme surface roles are currently unconverted placeholders resolving to `hsl(300, 100%, 50%)` — bright magenta. Affected: `--color-error-color`, `--color-on-error-color`, both `error-container` pairs, and the dark values for `background`, `surface`, `surface-dim`, `surface-bright`, `surface-container`, and `surface-container-{lowest,high,highest}`.

Consequence: the `danger` button variant renders magenta, and dark theme renders magenta surfaces. Build against these tokens — the names are correct and the values will be fixed upstream — but do not treat the current colour as intended, and do not work around it by hardcoding a substitute. Flag it if you hit it.

### Typography

Use the font shorthand tokens. `font` shorthand does **not** include `letter-spacing`, so set that separately when the token defines one.

```css
.pageTitle {
  font: var(--font-headline-medium);
  letter-spacing: var(--font-headline-medium-letter-spacing);
}

.bodyCopy {
  font: var(--font-body-small);
}

.muted {
  font: var(--font-label-large);
  color: var(--color-on-surface-variant-color);
}
```

Every scale token ships both a shorthand (`--font-body-small`) and longhands (`--font-body-small-font-size`, `-font-weight`, `-line-height`, `-letter-spacing`, `-font-family`). `font` shorthand does **not** cover `letter-spacing`, so always set it from its own variable. Never retype a literal like `-0.576px` when a variable holds that exact number.

Available scales: `--font-display-{large,medium,small}`, `--font-headline-{large,medium,small}`, `--font-title-{large,medium,small}`, `--font-body-{large,medium,small}`, `--font-label-{large,medium,small}`.

For one property only, use the longhand (`var(--font-body-small-font-size)`) rather than re-deriving a shorthand.

### Spacing

Multiples of 4px only: `4px`, `8px`, `12px`, `16px`, `24px`, `32px`, `48px`, `64px`. Prefer named CSS variables if the project adds a spacing scale later; until then use the literal scale values above.

### Radius

Small elements (badges, tags): `4px`. Buttons and inputs: `8px`. Cards and modals: `12px`. No other radius values.

### Mobile-First

```css
.card {
  padding: 16px;
  border-radius: 12px;
}

@media (min-width: 768px) {
  .card {
    padding: 24px;
  }
}
```

SellSnap's buyers are mostly on phones. Every component must work at 375px wide, and `/p/[slug]` must be fully usable there. Touch targets are at least 44px tall — check this on buttons, links, and anything tappable.

### Dark Theme

There is nothing to write. Using semantic roles means `data-theme="dark"` and `prefers-color-scheme: dark` already work. The moment you hardcode a color or target a primitive, that breaks — which is why it is banned above.

## Variants Without `class-variance-authority`

Put the variant in a `data-` attribute and let the stylesheet own the styling. The TSX stays free of class-name logic.

```tsx
// components/ui/Button.tsx

import { cn } from '@/lib/cn';
import styles from './Button.module.css';

type ButtonVariant = 'primary' | 'secondary' | 'ghost' | 'danger';
type ButtonSize = 'sm' | 'md' | 'lg';

type ButtonProps = React.ButtonHTMLAttributes<HTMLButtonElement> & {
  variant?: ButtonVariant;
  size?: ButtonSize;
};

export function Button({
  variant = 'primary',
  size = 'md',
  className,
  ...props
}: ButtonProps) {
  return (
    <button
      className={cn(styles.button, className)}
      data-variant={variant}
      data-size={size}
      {...props}
    />
  );
}
```

```css
/* components/ui/Button.module.css */

.button {
  display: inline-flex;
  align-items: center;
  justify-content: center;
  gap: 8px;
  min-height: 44px; /* touch target */
  padding: 0 16px;
  border: 1px solid transparent;
  border-radius: 8px;
  font: var(--font-body-small);
  color: var(--color-on-primary-color);
  background: var(--color-primary-color);
  transition: background-color 150ms ease, opacity 150ms ease;
  cursor: pointer;
}

.button:hover:not(:disabled) {
  opacity: 0.9;
}

.button:disabled {
  opacity: 0.5;
  cursor: not-allowed;
}

.button:focus-visible {
  outline: 2px solid var(--color-primary-color);
  outline-offset: 2px;
}

.button[data-variant='secondary'] {
  color: var(--color-on-surface-color);
  background: var(--color-surface-color);
  border-color: var(--color-outline-variant-color);
}

.button[data-variant='ghost'] {
  color: var(--color-on-surface-color);
  background: transparent;
}

.button[data-variant='danger'] {
  color: var(--color-on-error-color);
  background: var(--color-error-color);
}

/* Density changes padding and type size only. Height never drops below
   44px — a small button is still a touch target on a phone. */
.button[data-size='sm'] {
  padding: 0 12px;
  font: var(--font-label-large);
}

.button[data-size='lg'] {
  min-height: 48px;
  padding: 0 24px;
}

@media (min-width: 768px) {
  .button[data-size='lg'] {
    padding: 0 32px;
  }
}
```

Two things to copy from this: the variant union type declared by hand next to the props type, and `className` destructured out of `...props` so it cannot collide with the computed root class.

For sharing style blocks across classes inside the same file, use the native CSS Modules `composes` rather than copy-pasting:

```css
.truncate {
  overflow: hidden;
  text-overflow: ellipsis;
  white-space: nowrap;
}

.productTitle {
  composes: truncate;
  font: var(--font-title-medium);
  color: var(--color-on-surface-color);
}
```

## Accessibility

Every interactive element needs a keyboard-reachable focus state. Style `:focus-visible` explicitly in the module — there is no utility class to fall back on.

```css
.control:focus-visible {
  outline: 2px solid var(--color-primary-color);
  outline-offset: 2px;
}
```

- Buttons with no visible text need `aria-label`. Icon-only buttons are the usual offender and they do not ship without one.
- Form inputs need a real `<label htmlFor>` paired with the input `id`. Error text is wired via `aria-describedby`.
- Images always get `alt`. Decorative images get `alt=""`. Never omit the attribute.
- Status and validation text should not rely on color alone; pair it with text or an icon.
- Target 375px and test keyboard-only navigation. Tab order should follow visual order.

---

## Props to Avoid

- No raw color props (`color="red"`). Use a variant.
- No raw pixel size props. Use the size variants.
- No `style` prop except for values that genuinely cannot live in CSS.
- No props that only restate what CSS Modules can do.

---

## Verification

Before calling a component done:

- Default appearance, every variant, every size
- Disabled state where applicable
- Focus state (tab into it — it must be visible)
- Hover state
- 375px viewport, then 768px
- Touch targets at least 44px
- Dark theme renders correctly (toggle `data-theme="dark"` on `<html>`)
- No hardcoded hex / hsl / px font sizes in the module
- A screen-reader pass on labels and aria attributes

Domain components (product, dashboard) can be reviewed in place on the relevant page. For a new primitive, a temporary dev route at `app/_dev/page.tsx` that renders every variant is a reasonable way to eyeball it — there is no component gallery or Storybook in this project, and the route must not ship. Delete it when you are done.

---

## Common Mistakes

- Creating a new primitive when an existing one would work with one more variant. Extend, do not duplicate.
- Reaching for Tailwind out of habit. It is not installed and is explicitly banned.
- Using primitive color variables instead of semantic roles, which quietly kills dark theme.
- Hardcoding hex, `hsl()`, or px font sizes in component CSS.
- Forgetting the 44px minimum touch target.
- Writing desktop styles first and retrofitting mobile.
- Making a component a client component because it was easier.
- Forgetting `className` on a component that will need different layout in different places.
- Putting logic inside the JSX. Extract it to a named constant or helper above the return.
- Editing `tokens/tokens.css`. It is generated. Ask for a token to be added instead.
